UniPAD：面向自动驾驶的通用预训练范式

UniPAD: A Universal Pre-training Paradigm for Autonomous Driving · arXiv 2310.08370 · github.com/Nightmare-n/UniPAD · nuScenes · CVPR 2024

§1Motivation

问题是什么、难在哪、别人怎么解、UniPAD 怎么解。

自动驾驶的 3D 感知模型高度依赖预训练：3D 标注成本高，更现实的路径是先用海量无标注数据把骨干网络练好。但点云与图像差异很大，2D 的成熟方法直接迁移效果有限，原因见 1.1。UniPAD 的思路是：遮住输入的一部分，让网络从剩余观测中学出 3D 特征场，再把特征场渲染成 RGB 图或深度图，和真实传感器拍到的结果对比，误差全部回传。监督信号完全来自数据本身，不需要任何人工标注。整套方法概括起来就是：用掩码重建做 3D 预训练的统一范式，检测、分割、占用共享一条预训练链路。

1.1面临的问题和难点

点云数据先天稀疏不均

图像是规则的像素网格，点云则稀疏、无序、分布不均：远处一辆车只有十几个点，近处地面却有海量点；传感器位置和遮挡关系都会改变点的分布。

结果是，2D 中效果很好的 MAE（遮住再恢复）迁移到 3D 效果有限：被遮区域可能本来就只有很少的点，恢复输入这个任务过于简单，学不到充分的表征。

已有代理任务的监督太粗

对比学习需要精心构造正负样本对，选择不当会让训练偏离目标，计算开销也大；体素级的 MAE（Voxel-MAE、GD-MAE）在粗体素上做重建，监督只有"整块有没有点"这么粗的粒度，精细几何学不到。

这些方法都在 3D 域内部进行，丢掉了"这个世界长什么样"的先验知识。

1.2别人是怎么解决的

路线代表工作做法 & 痛点
对比学习 PointContrast / Pri3D / Pixel-to-Point (P2P) 两个视角变换下拉近相同物理点的特征、推远不同的点。麻烦在于正负样本不好挑、训练开销大，P2P 还得做跨模态对齐。
MAE 式重建 Voxel-MAE / GD-MAE / ACT 遮住点云一部分，让网络在体素域或特征域恢复。但体素监督只有"一整块有没有点"这种粗粒度，几何学不细；而且点云冗余大，题目偏简单。
表面重建 ALSO 隐式 SDF 重建整个表面作为代理任务。主要给点云设计的，不好迁移给 2D 图像骨干。
2D 预训练迁移 ImageNet 初始化 / nuImages 检测器初始化 直接用 2D 预训练权重初始化图像骨干。问题是缺 3D 先验，或者干脆要标注：论文表 3 里即使拿 FCOS3D 带 3D 标注训出的权重，也只涨 6.5 NDS，UniPAD 涨 7.7。

1.3UniPAD 是怎么解决的

核心思想：3D 表征好不好，看它能不能画出真实世界。如果一个 3D 特征场真的记住了场景的几何（哪里有表面、离多远）和外观（什么颜色、什么纹理），那从任意角度把它投影渲染成 2D 图，结果就应该和真实相机拍到的一样。

预训练任务就可以这么定：遮住输入，编码成 3D 特征场，可微渲染出 RGB 或深度图，和真实图算 L1 误差，然后反向传播。渲染是可微的，误差能一路传回编码器。

这个任务的监督是逐像素、连续的，不用挑正负样本，也不受体素粒度的限制。约束也比 MAE 强得多：MAE 只要求恢复被遮住的输入本身，UniPAD 要求重建出的 3D 表征经得起任意视角的检验，渲染结果对不对，几何结构和外观特征两个维度都逃不掉。

1.4优点和效果

  • 体渲染天然就是从 3D 特征到 2D 图像的桥，所以点云和多视角图像可以各自先变成同一种 3D 体素表征再渲染，一套流程同时覆盖两种模态，融合模态直接将两份特征相加。
  • 监督信号就是传感器自己拍到的数据，不需要任何标注，而且是逐像素连续的，顺便避开了对比学习里挑正负样本的麻烦。
  • 用起来也不挑：预训练只涉及编码器和渲染解码器，下游随便换检测头、分割头，编码器权重直接搬走。论文在 7 种骨干、2 类任务上都验证过。
  • 提升幅度可观：LiDAR 检测从 67.7 到 70.6 NDS，少数据场景提升 9.1，分割达到 79.4 mIoU，全面超过对比学习和 MAE 式重建等路线（论文表 4）。
  • 显存开销可控：配合三种节省内存的 ray 采样策略（§2.3），自动驾驶级别的大场景用 4 张 A100 即可训练。
  • 效果上，LiDAR、相机、融合三种模态的检测基线全部提升，少数据场景最高 +9.1 NDS，语义分割达到 79.4 mIoU；具体数字和对比见 §4。

§2Architecture

先看双链路总流程（模块级视图，每个模块标真实输入输出 shape），细节留给下面三个子模块小节。

2.1Overall Pipeline

图 2-1 · UniPAD 预训练总流程（LiDAR 主线 + Camera 支线）。shape 与超参全部取自官方 config，B=4（每 GPU batch）。
输入 编码器 遮罩操作 渲染解码器 输出 数据流 监督/控制流
  • LiDAR 链路先体素化再编码。10 帧 LiDAR 点（约 34 万个，每个点 5 维：坐标、强度、时间戳）先过滤距离，只留 3 到 100 米内的点，再按 0.075×0.075×0.2 米的体素做划分（网格 41×1440×1440，最多留 12 万个非空体素），HardVFE 把每个格子里最多 10 个点平均成一个 5 维特征。
  • 遮罩作用在体素上，比例相当高：以 8×8×8 的块为单位随机移除 80%。被移除的体素直接从输入中去掉，不进网络（learnable=False，也没有替换成可学习 token），只保留 20% 进入 SparseUNet，四个 stage 逐级 2 倍下采样，稀疏卷积只在非空位置计算，最后 1×1 卷积升到 256 维变回稠密张量 [B,256,5,180,180]，再过 SECOND3D 骨干和 3D FPN 融合一下，分辨率不变。
  • Camera 链路（相机模态预训练时才有）：6 张图像 pad 到 928×1600，在 1/32 分辨率的 29×50 网格上随机遮 30%，被遮的像素直接置 0。ConvNeXt-S 被改成 SparK 式的稀疏卷积，只在可见区域算，用 ImageNet 权重初始化。特征过 FPN 降到 256 维；旁边一个 ComplexDepth 深度头预测每个像素的深度分布（118 档、每档 0.5 米、覆盖 1~60 米）。LSS 体素池化将 2D 特征与深度分布相乘后聚合到 3D 体素格，得到和 LiDAR 支路完全同构的 [B,256,5,180,180]，这就是论文说的统一 3D 体积表征。
  • 汇聚之后走一个 3×3×3 的 Conv3d，把 256 维压到 32 维。这层看似简单，消融实验中去掉会下降 1.8~2.7 NDS。
  • 一个容易忽略的细节：渲染的 ray 采样自 6 个相机的图像，每相机 512 条。方向由相机中心与像素的连线确定，GT RGB 取该像素的颜色值，GT 深度取投影落在该像素的 LiDAR 点的距离。所以 LiDAR 预训练虽然不编码图像，监督信号却完全来自图像和点云的投影关系。
  • NeuS 渲染器计算最终输出：每条 ray 先和场景包围盒求交拿到 near 和 far，沿途均匀采 72 个点、表面附近再加密 24 个（共 96 个）；每个点从特征场三线性插值出 32 维特征，过 SDF MLP 得到符号距离 sⱼ 和几何特征 hⱼ，过 RGB MLP 得到颜色 cⱼ，最后用遮挡感知的权重 wⱼ=Tⱼαⱼ加权求和，得到这条 ray 的 RGB 和深度，与 GT 计算 L1。
  • 预训练结束后，编码器（SparseUNet 或 ConvNeXt，加上 FPN 和 LSS）的权重保留下来，渲染解码器整体丢弃，替换为检测或分割头做 finetune（§2.4）。

两条支路按模态单独启用：LiDAR 版预训练只配点云编码器，图像不进骨干，只用来采 ray 和提供 GT；Camera 版正好相反，点云不进编码器，而是投影到图像上提供深度 GT。图里两条都画出来，是因为两边的编码器和渲染流程同构，融合检测时两条同时启用、特征相加。

§2.2Masked Sparse Encoder

两条支路的遮罩方式差别很大，光看论文那张总图很容易搞混，这里分别说明：

LiDAR 支路（Block 删除式）Camera 支路（置零稀疏式）
遮罩单位8×8×8 体素块（block）1/32 分辨率 patch（29×50 网格）
遮罩比例0.8（点云空间冗余大）0.3（渲染重建任务难，遮多了不可解，论文表 8）
被遮部分怎么办直接删除，不进网络（learnable=False）像素置零，位置保留，卷积跳过
计算方式稀疏卷积只在可见体素上算ConvNeXt 改造成 SparK 稀疏卷积，只在可见 patch 上算
编码器输出[B,256,5,180,180][B,6,768,29,50] → FPN [B,6,256,29,50]

2.2.1LiDAR 的 Block Mask 是怎么操作的（一步一图）

  • 为什么按块遮、不逐格遮？逐格遮留下的邻近信息太多，被遮格子的特征靠插值就能估计出来，任务过于简单；8³ 的块一遮一大片，网络必须掌握大范围上下文才能恢复。
  • 3D 用 80% 的遮罩比例、图像只用 30%，原因不同：点云空间冗余大，一辆车几百个点的特征高度相似，遮掉 80% 信息仍然充分；而"从 3D 特征场渲染回 2D 图像"本身比图像到图像的重建难得多，图像遮太多任务就无解。论文表 8 从 0.1 试到 0.9，0.3 最优（32.9 NDS）。
  • 被移除的 80% 没有替换成 token：learnable=False 时，代码直接用布尔索引 voxel_features[voxel_active] 过滤掉这些体素；也支持 learnable=True 替换为可学习 token 的方案，但官方配置未启用。
  • 块大小 8 与编码器的 8 倍下采样正好对应：一个块恰好浓缩成特征图上的一格，渲染时需要恢复的正是这些格子。
  • mask 的结果会记在一个全局变量里（sparse_utils._cur_active_voxel），采样 ray 时可以只选被遮区域，不过发布的 config 未启用，采样在全图进行。
  • 编码器本体就是 UVTR 用的那套 SparseUNet，四个 stage 通道从 16 到 128，前三段各做一次 2 倍下采样，最后 1×1 卷积升到 256 维并转回稠密张量。预训练学习的主体就是它，finetune 时权重原样保留。

2.2.2Camera 的 Patch Mask（置零 + 稀疏卷积，一步一图）

  • 图像这边是置零，不是删除。被选中的 30% patch 像素乘 0，张量形状不变。ConvNeXt 的卷积和归一化都换成了稀疏版（SparK 的做法），只在可见 patch 上计算，被遮位置不消耗算力也不产生梯度。
  • 初始化也有讲究：ConvNeXt-S 用 ImageNet 预训练权重初始化，还冻结了第一层。相当于先具备 2D 图像理解能力，再学习从 3D 视角理解图像。
  • 输出端同样通过补零恢复稠密：骨干输出 [B,6,768,29,50]（只计算了约 70% 的位置），被遮 patch 位置的特征为 0，后续 FPN 和 LSS 正常进行。

§2.3Volumetric Rendering

渲染解码器只解决一个问题：给定一条光线，它的颜色是什么、终点在哪里。先看 head 的整体数据流（下图，shape 级），再逐条 ray 展开算法细节（下面的 8 张卡）。训练时每相机采 512 条 ray，6 个相机共 3072 条，每条都按这个流程处理。

这条流水线的 shape 主线：[B,256,5,180,180] 经 render_conv 压到 [B,32,5,180,180]，3072×96 ≈ 29.5 万个采样点各插值出 32 维特征，过两个窄 MLP，最后积分回每 ray 两个输出。render_conv 把通道压到 32 是算出来的账：查询点数量（29.5 万）远大于体素数，通道窄 8 倍，插值和 MLP 的乘法就省 8 倍；SDF/RGB 头的隐层都只有 16 维，因为几何信息已经编码在特征场里，MLP 只负责"查到的特征 → SDF/颜色"这步映射，窄一点反而抗过拟合；全程可微，L1 的梯度沿积分 → MLP → 插值 → Conv3d 一路传回编码器，这是"渲染能当预训练代理任务"的前提。

2.3.1两个关键公式

ŶRGBi = Σj=1..D wj · cj     Ŷdepthi = Σj wj · tj
论文 Eq.2：一条 ray 的渲染值就是沿途 96 个采样点（72 均匀 + 24 加密）的加权平均，深度在代码里还会除以 Σwⱼ 做归一化，wⱼ 是每个点的权重。空气中的采样点权重接近零，物体表面附近的采样点权重最大，最终值基本由表面附近的点决定。
wj = Tj · αj,   Tj = Πk<j(1 − αk)     αj = max( (σ(sj) − σ(sj+1)) / σ(sj), 0 ),  σ = sigmoid
论文 Eq.3（NeuS 风格）。把 ray 想成雾里的一束手电筒光：Tⱼ 就是光穿过前面几段后还剩多少，前面碰到的东西越实（α 越大），漏到后面的光越少，所以第一个实体表面会吃掉几乎全部权重，后面的点自动没声。sⱼ 是符号距离（物体外为正、里面为负），相邻两点 SDF 的 sigmoid 差变化大，说明表面就在这附近；代码里还用视线和法向的夹角做了修正。
  • 特征场是连续的：采样点用三线性插值从 [B,32,5,180,180] 里取 32 维特征，体素只有 0.6m 粗，但插值让任意位置都能查询。
  • SDF 头走跳连路线，每层把特征 fⱼ 注进去（x = Linear(x + fc_c(fⱼ))，类似 FiLM），hidden 只有 16 维，SDF/RGB 头分别为 5/3 个块；SDF 头输出符号距离 sⱼ 和 16 维几何特征 hⱼ。
  • 法向 nⱼ 用 autograd 对采样点坐标求 SDF 梯度得到，create_graph=True 保证梯度能继续回传到编码器，不需要额外监督。
  • RGB 头的输入拼接是 cat(d, fⱼ, nⱼ, hⱼ)：视线方向 3 维 + 场特征 32 维 + 法向 3 维 + 几何特征 16 维，共 54 维，不含采样点坐标。
  • 用 NeuS 不用原版 NeRF：NeuS 的权重无偏、表面更准（表 11：比 UniSurf +0.4、VolSDF +0.1 NDS），渲染器的质量直接决定预训练学到的表征。
  • 两轮采样降低计算量：先均匀采 72 点，occupancy（sigmoid(−10·sdf)）指示表面位置后，再在表面附近加密 24 点（共 96 点），比全程密采省大约三四倍计算。
  • 训练只在 3072 条采样的 ray 上算损失，不渲染整图（Memory-friendly Ray Sampling）；测试脚本 sample_rays_test 才会按半分辨率铺满全图渲染，论文图 3 的效果图就是这么生成的。

§2.4UVTR Detector

图 2-4 · 权重交接：渲染解码器丢弃，编码器保留并 load_from 给 DETR 式检测头。
  • 交接很干净。finetune 用的编码器和预训练是同一个类、同一份 config，唯一区别是去掉 mae_cfg（不再遮罩，全量输入），然后 load_from 预训练的 checkpoint。论文表 14 拆解了各部分贡献：编码器占 6.8 NDS，是主要部分，FPN 和视角变换分别占 0.2 和 0.7。
  • 检测头是 DETR 家族的查询式头：一组可学习的 query 用 deformable 风格的交叉注意力（UniCrossAttenV2）从 3D 特征里定位目标，训练时加 DN-DETR 式的去噪 query 加速收敛，每个 query 输出 10 类分数加一个 3D 框。
  • 相机模态交接的东西多一点：预训练的 ConvNeXt 骨干、FPN、深度头、LSS 视角变换全部留给相机检测器，LiDAR 支路同理。融合模型 UVTR-M 就是两边权重各拿各的。

§3Loss

3.1预训练总损失：就两个 L1

L = λRGB/K · Σi=1..K |ŶRGBi − YRGBi|  +  λdepth/K⁺ · Σi=1..K⁺ |Ŷdepthi − Ydepthi|
论文 Eq.4。K 是 ray 总数（3072 = 6 相机 × 512），K⁺ 是其中有 GT 深度的那部分，两个 λ 都是 10（相机版）。预训练实际在做两个回归：预测每个采样像素的颜色（RGB，仅相机模态启用），以及每条光线的终点距离（深度）。预测值由渲染给出，目标值来自传感器本身，L1 差距回传给编码器，一直调到特征场能自洽地解释真实观测为止。
图 3-1 · 预训练损失：两条支路各算一个 L1（深度全模态、RGB 仅相机），求和后回传。
  • 深度 GT 的排除机制值得细看。LiDAR 点投到 6 张图上，只有被投中的像素有 GT 深度，没投中的 ray 深度记 −1，算 loss 时用 valid_gt_mask = depth_gt > 0 整条剔掉。天空和远处区域因此被排除，监督集中在有物体的位置。
  • LiDAR 预训练只用深度损失：LiDAR config 里 rgb_loss=0，点云本身没有颜色信息。相机版两个损失都用，各乘 10。
  • 代码中还实现了四个正则项（free_space、sdf、eikonal、稀疏点 SDF 监督），但发布的两个 config 均未设置权重，全部不启用。因此按官方配置复现，预训练损失就是两个 L1。
  • 注意场景归一化：所有坐标和深度都乘 scale_factor=1/54（pc_range 最长边），场景缩放到约 ±1 的立方体内再渲染，数值更稳定；GT 做同样缩放，口径一致。
  • 推理（可视化）时不算 loss。测试脚本按半分辨率铺满全图渲染，把 RGB 和深度图存成 pkl，论文图 3 的效果图就是这么出的。预训练本身没有评测指标，效果好不好，要等 finetune 之后才见分晓。

3.2finetune 损失：DETR 式匹配 + focal/L1（简述）

  • 匈牙利匹配把 N 个 query 的预测和 GT 框一对一配对（代价是分类加框距离），只有配上的 query 才有监督，避免多个 query 都去预测同一个目标。
  • 分类用 focal（sigmoid，应付 10 类不平衡），框回归用 L1（中心、尺寸、朝向 sin/cos）。解码器每一层都有辅助损失，DN 去噪 query 还额外提供正样本。
  • 相机版另有深度分布的 BCE 辅助损失，挂在 LSS 的深度头上。注意预训练 config 里它的权重是 [0.0]，预训练阶段未启用，finetune 时才启用。

§5Conclusion

5.1这篇论文证明了什么

  • 核心想法是成立的：要求网络从 3D 特征场渲染出与真实世界一致的投影，确实能驱动它学到有效的 3D 表征。渲染要准确，几何（表面位置、距离）和外观（颜色、纹理）缺一不可。
  • 三种模态都有效：同一套渲染解码器，LiDAR、相机、融合在 20% 数据 finetune 口径下分别提升 9.1、7.7、6.9 NDS，全量数据约 3 个点。
  • 与其他预训练方法相比也占优：ALSO（表面重建）、GD-MAE（MAE 式重建）、P2P（像素到点对比学习），以及三种用现成权重初始化的方案，UniPAD 均优于它们（论文表 3、4），而且不需要设计正负样本，也不需要额外标注。
  • 换骨干同样有效：ConvNeXt 三个尺寸、VoxelNet，以及 BEVDet、BEVDepth、BEVFormer 三种视角变换，接入后都有 5~9 NDS 的提升，说明方法不依赖特定结构。
  • 分割从 73.3 提升到 79.4 mIoU（验证集最优），测试集 81.1。检测和分割同时提升，说明学到的是通用 3D 表征，不是为检测定制的特征。

5.2局限（论文自己说的，加上读代码看出来的）

  • 显存随体素分辨率增长（论文明确提到）：统一体积是显式的 [B,C,5,180,180]，提高分辨率会显著增加显存，这是显式体素化的固有问题。
  • 依赖标定和多传感器对齐（从代码看）：采 ray、投影 GT 深度、LSS 变换都依赖 lidar2img 和 lidar2cam 矩阵，标定误差会直接转化为监督噪声；LiDAR 版预训练也必须同时加载图像。
  • 两阶段流程成本高：预训练 12 个 epoch、finetune 20 个，总开销超过端到端方案；渲染解码器的全部参数在 finetune 时被丢弃，这部分计算没有被复用。
  • NeuS 逐 ray 计算的速度一般：3072 条 ray × 96 个采样点 × 两个 MLP，依靠 fp16 和稀疏采样控制开销；三种采样策略本质上是在监督密度和显存之间权衡。

5.3后续计划与延伸方向

  • 论文指出的方向：用 SAM 这类 2D 大模型为渲染增加语义监督，目标从颜色一致扩展到分割一致，把 2D 域的语义知识引入 3D 表征。
  • 作者团队的后续工作已经出现：同一团队将这套范式扩展为 PonderV2（T-PAMI 2025），覆盖室内场景和更多任务，读完 UniPAD 可以接着看它。
  • 可预期的技术升级：渲染器从 NeuS 换成 3D Gaussian Splatting（更快、质量更高）；显式体素换稀疏或混合表征，缓解分辨率与显存的矛盾；两阶段改为联合训练或在线蒸馏。
